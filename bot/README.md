# بات مستقل آکادمی سبحان صمدی (فاز ۱)

این یک سرویس مستقل است که مستقیم به Telegram API وصل می‌شود و دیگر از پشت
n8n رد نمی‌شود. هدف: حتی اگر n8n یا دیتابیس مشترکش قطع شد، دکمه‌های اصلی
بات (منوی /start) همچنان کار کنند.

**وضعیت فعلی:** منوی اصلی، کتابخانه، دوره‌های رایگان، اکسپرت، پشتیبانی،
ثبت‌نام و **تقویم اقتصادی** روی همین سرویس اجرا می‌شوند. از n8n فقط برای
تحلیل هوش مصنوعی و جمع‌آوری داده‌ی تقویم استفاده می‌شود.

## تقویم اقتصادی: آینه‌ی داده در D1

داده‌ی تقویم را همچنان زمان‌بندهای n8n جمع می‌کنند. اگر بات موقع هر ضربه‌ی
کاربر مستقیم از n8n می‌خواند، تقویم دقیقاً به همان چیزی وابسته می‌ماند که
مدام قطع می‌شد. به‌جای آن یک Cron در همین ورکر هر ۱۰ دقیقه داده را می‌کشد
و در D1 می‌ریزد؛ پاسخ کاربر همیشه از D1 خوانده می‌شود، پس قطعی n8n تقویم
را از کار نمی‌اندازد - فقط داده کمی کهنه می‌شود.

برای فعال شدنش سه مقدار در **Settings → Variables and Secrets** لازم است:

| نام | نوع | مقدار |
|---|---|---|
| `ECON_EXPORT_URL` | Variable | `https://96825.7host.cloud/webhook/econ/export` |
| `ECON_EXPLAIN_URL` | Variable | `https://96825.7host.cloud/webhook/econ/explain` |
| `ECON_EXPORT_KEY` | Secret | کلید مشترک هر دو گردش‌کار تقویم در n8n |

تا وقتی این‌ها ست نشوند، دکمه‌های تقویم پیام «تقویم هنوز همگام‌سازی نشده
است» می‌دهند - نه خطای داخلی. جدول‌های آینه را خودِ اولین همگام‌سازی
موفق می‌سازد (`schema-econ.sql` فقط نسخه‌ی مستندشده‌ی همان است).

## دو گردش‌کار n8n که باقی مانده‌اند

| گردش‌کار | مسیر | کارش |
|---|---|---|
| `WF-Econ-Export` | `POST /webhook/econ/export` | فقط می‌خواند: رویدادها، برچسب‌ها، تعطیلات و کش را برای آینه برمی‌گرداند. کد SDK آن در `n8n-econ-export.sdk.js` است. |
| `WF-Econ-Explain` | `POST /webhook/econ/explain` | تنها جایی که هوش مصنوعی اجرا می‌شود. ورکر زمینه را می‌سازد و می‌فرستد؛ n8n یا پاسخِ تازه‌ی کش (TTL پانزده دقیقه، مثل قبل) را می‌دهد یا از Gemini یکی می‌گیرد و کش می‌کند. |

هیچ‌کدام به `WF-Economic-Calendar` دست نمی‌زنند؛ آن گردش‌کار (۱۳۴ نود، چهار
زمان‌بند فعال) دست‌نخورده به جمع‌آوری داده ادامه می‌دهد.

> چرا زمینه را ورکر می‌سازد و n8n نه: تبدیل جلالی و ساعت تهران همین حالا
> در ورکر هست. اگر n8n هم نسخه‌ی خودش را نگه می‌داشت، دو پیاده‌سازی
> داشتیم که با هم از هم دور می‌افتادند.

## چرا Cloudflare Workers

نیازی به Docker یا مدیریت سرور نیست، و بر خلاف پلن رایگان اغلب پلتفرم‌ها،
اینجا **هیچ حالت خواب/بیدارشدنی وجود ندارد** - چون سرویس یک سرور دائمی
نیست؛ هر پیام یک اجرای مستقل و آنی (چند میلی‌ثانیه) روی شبکه‌ی جهانی
Cloudflare است. سقف رایگان تا ۱۰۰,۰۰۰ درخواست در روز است که برای این بات
به‌زودی‌ها کافی خواهد بود.

## دیپلوی از طریق پنل Cloudflare (بدون خط‌فرمان)

۱. وارد [dash.cloudflare.com](https://dash.cloudflare.com) شوید (اگر
   حساب ندارید، ساخت آن رایگان و بدون نیاز به کارت است).
۲. از منو **Workers & Pages → Create → Import a repository** را بزنید و
   حساب گیت‌هابتان را وصل کنید.
۳. ریپو `mehdifx21hoseini-debug/sobhansamadi` را انتخاب کنید.
۴. در تنظیمات بیلد:
   - **Root directory**: `bot`
   - Cloudflare خودش فایل `wrangler.toml` را در همین پوشه پیدا و از آن
     برای بیلد و دیپلوی استفاده می‌کند - نیازی به تنظیم دستی build/start
     command نیست.
۵. قبل از دیپلوی یا بلافاصله بعدش، به تب **Settings → Variables and
   Secrets** سرویس بروید و یک **Secret** (نه Variable عادی، چون توکن
   باید رمزنگاری‌شده ذخیره شود) با نام `BOT_TOKEN` و مقدار توکن واقعی
   بات اضافه کنید.
۶. Deploy را بزنید. بعد از اتمام، آدرسی مثل
   `https://sobhan-academy-bot.<your-subdomain>.workers.dev` می‌گیرید.

## وصل کردن Telegram به این آدرس (setWebhook)

با آدرسی که از Cloudflare گرفتید (و توکن واقعی) این دستور را یک‌بار در
ترمینال اجرا کنید:

```bash
curl -F "url=https://sobhan-academy-bot.<your-subdomain>.workers.dev/webhook/<BOT_TOKEN>" \
  https://api.telegram.org/bot<BOT_TOKEN>/setWebhook
```

اگر خروجی `"ok":true` بود، از این لحظه تلگرام پیام‌ها را به این سرویس جدید
می‌فرستد، نه به n8n. برای برگشت به حالت قبل کافی‌ست دوباره webhook قبلی
(روی n8n) را ست کنید.

> پیشنهاد: قبل از سوییچ کردن بات اصلی، همین مراحل را با یک **بات تست جدا**
> (توکن جدید از BotFather) امتحان کنید تا کاربران واقعی درگیر تست نشوند.

## توسعه‌ی محلی (اختیاری)

```bash
cd bot
npm install
cp .dev.vars.example .dev.vars   # و BOT_TOKEN را داخلش پر کنید
npm run dev
```

## رساندن لیدهای ربات به CRM

ورکر لید را در D1 می‌نویسد، ولی CRM لیدها را از جدول‌های n8n می‌خواند. بدون
پل بین این دو، هر ثبت‌نامی که از ربات می‌آید در CRM دیده نمی‌شود و مشاور
هرگز با آن مشتری تماس نمی‌گیرد.

چون n8n مرتب قطع می‌شود، فرستادن در همان لحظه کافی نیست: هر قطعی یعنی یک
مشتریِ از‌دست‌رفته. به‌جای آن **صندوق خروجی** داریم:

1. لید در جدول `leads` نوشته می‌شود — رکورد دائمی، هرگز گم نمی‌شود
2. یک ردیف هم در `lead_outbox` می‌نشیند
3. بلافاصله **بعد از پاسخ به کاربر** یک‌بار تلاش می‌شود بفرستیم
4. اگر نشد، همان Cron هر ده دقیقه دوباره تلاش می‌کند

یعنی قطعی n8n فقط تاخیر می‌سازد، نه از دست رفتن داده.

| نام | نوع | مقدار |
|---|---|---|
| `CRM_LEAD_INTAKE_URL` | Variable | `https://96825.7host.cloud/webhook/crm/lead/bot-intake` |
| `CRM_LEAD_INTAKE_KEY` | Secret | کلید گردش‌کار `WF-Bot-Lead-Intake` |

اگر این دو ست نشوند، لیدها بی‌سروصدا در صف می‌مانند (چیزی خراب نمی‌شود و
هیچ داده‌ای از بین نمی‌رود)، ولی در CRM ظاهر نمی‌شوند.

> حذف تکراری‌ها با **شماره تلفن** انجام می‌شود: اگر همان شماره قبلاً لید
> داشته باشد، یادداشت تازه به پرونده‌ی خودش اضافه می‌شود و ردیف دوم ساخته
> نمی‌شود — همان قاعده‌ای که فرم منتورینگ سایت دارد.
